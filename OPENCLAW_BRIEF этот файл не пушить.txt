# NEXUM Bot — Full Development Brief for OpenClaw Agent

## Project overview

NEXUM is a production Telegram bot (TypeScript + grammy) deployed on Railway.
It is a personal AI assistant with mini web apps, PC agent, and all OpenClaw capabilities adapted for Telegram.

Repository: https://github.com/thenexumai/nexum-bot (branch: main)
Live URL: https://nexum-bot-production-ae70.up.railway.app
Bot: @ainexum_bot

## Tech stack

- Runtime: Node.js 20, TypeScript, ts-node
- Bot framework: grammy
- Database: SQLite via better-sqlite3
- Server: Express + WebSocket (ws)
- Scheduler: node-cron
- Browser automation: Playwright (chromium)
- PDF: pdf-parse
- TTS: edge-tts (Python CLI)
- STT: Groq Whisper API
- Deployment: Railway via Dockerfile, auto-deploy on push to main

## What needs to be fixed / completed

### 1. CRITICAL: Language detection is broken
The bot often replies in the wrong language. It MUST always reply in the exact language the user wrote in.
- Russian input → Russian reply
- English input → English reply  
- Uzbek input → Uzbek reply
- Mixed → match the dominant language
This should be enforced in the system prompt AND as a post-processing check.

### 2. Personality still sounds robotic
The bot should sound exactly like Claude — warm, direct, intellectually curious, with real opinions.
When asked "what can you do" it should NOT list capabilities. It should answer naturally.
When greeted, respond naturally in 1-2 sentences, not a paragraph.
The system prompt identity section needs to produce Claude-quality responses.

### 3. Mini apps not syncing with bot
When the bot records a finance entry via tool, the mini app Finance page should show it.
The issue: uid resolution in mini apps. The Telegram WebApp sends initData which contains user.id.
The server's validateInitData() must correctly extract uid from initData.
All mini app HTML files use `tg.initData` but the server sometimes rejects valid signatures.
Fix: make getUid() accept uid from query param OR body as fallback (for development), but in production use the real initData validation.

### 4. Browser tool screenshots not sent to user
When browser tool returns `SCREENSHOT_BASE64:...`, the execute() function should send it as a photo to the user via bot.api.sendPhoto(). Currently this is wired but may not work because bot reference is not always available.
Fix: ensure the `bot` reference is passed through opts properly.

### 5. PC Agent commands are stubs
/run, /screenshot, /sysinfo, /ps, /kill etc. currently just say "requested from agent" without actually relaying to the PC agent WebSocket.
The server.ts has a `sendToAgent()` function. The commands.ts needs to import and call it.
Fix: in commands.ts, import the server app reference and relay commands properly.

### 6. Streaming is sometimes choppy or double-sends
The draft-stream throttle works but sometimes sends the final message twice (once from stop() and once from the handler fallback).
Fix: in handler.ts, only send fallback if `draft.messageId() == null` AND no error occurred.

### 7. /help command not clean
/help shows English text even for Russian users. Should detect language.
Also the command list is too long for the Telegram message limit in some cases.

### 8. Missing: /model command to switch AI provider preference
Users should be able to type `/model groq` to prefer Groq, etc.
Save preference to memory/user_api_keys table and use it in router.ts.

### 9. Missing: proper /status with real provider health check
/status should actually ping providers to check which ones respond.
Show latency for each available provider.

### 10. Missing: conversation context in groups
In group chats, the bot only has 1 conversation history per uid, not per group.
Should store conversations per (uid, chat_id) pair so group context is separate from DM context.

## Notes on streaming (OpenClaw draft-stream pattern)

The streaming works like this:
1. Show typing indicator immediately
2. Create draft stream (throttle: 1000ms, minInitialChars: 60)
3. AI streams tokens via SSE (Groq/Cerebras) → draft.update(accumulated)
4. Every 1000ms → editMessageText with current accumulated text
5. On completion → draft.stop() → final flush
6. Keep typing indicator alive every 4500ms during generation

This is the exact same mechanism as OpenClaw's createTelegramDraftStream.
Do not change this — it works correctly.

## Notes on tool syntax

Tools are called by the AI using XML:
```xml
<tool name="finance_add" type="income" amount="5000" category="salary" note="March salary" />
```

The executor parses these with regex, executes the handlers, injects results back as a user message, and the AI continues. This loop runs up to 10 times per message.

The tool XML must NEVER be shown to the user. executor.ts has stripToolXML() that cleans the final response.

## Notes on mini apps

Mini apps are Telegram WebApps. They open in the Telegram client and communicate with the Express server via REST API.

When opened, `window.Telegram.WebApp.initData` contains a signed string with user.id.
The server validates this with HMAC-SHA256 using the bot token.
After validation, getUid() returns the user's Telegram ID which is used to query SQLite.

The fix needed: make sure the uid extracted from initData matches the uid used by the bot to store data.
